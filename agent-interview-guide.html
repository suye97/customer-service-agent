把 Agent 从演示
讲到生产现场。

围绕 3C 租赁客服的商品检索、订单与流水查询、身份鉴权、会话恢复和失败处理。每题附参考答法与可能的追问。

先把 Recall@10 和 MRR 讲明白

Recall@10（前 10 召回率）：某个问题真正相关的商品中，有多少出现在向量检索的前 10 个结果里。假设相关商品为 A、B、C，前 10 只找到 A、B，这题的 Recall@10 就是 2/3。

MRR（平均倒数排名）：每题只看第一个相关商品出现的名次。排第 1 得 1，排第 2 得 1/2，排第 5 得 1/5；没进结果得 0。把所有有相关商品的题目取平均，就是 MRR。

单题 Recall@10 = 前 10 命中的相关商品数 ÷ 该题相关商品总数单题倒数排名 = 1 ÷ 第一个相关商品的名次项目实测 = 16 条正例的逐题平均：Recall@10 ≈ 0.839，MRR = 0.750
这次真实 Milvus 评测共 20 题，其中 16 题存在相关商品；4 个“本就没有符合商品”的负例不进入原始向量 Recall@10 / MRR 分母，但会进入最终候选集合的正确性统计。过滤后的 20/20 完全匹配，不能写成向量 Recall@10 = 100%。

面试时的边界：Recall@10 衡量“有没有捞到”，MRR 衡量“第一个相关结果靠不靠前”；二者都不能单独证明最终回答没有幻觉，也不能证明订单鉴权正确。

意图与流程编排

规则、模型与 LangGraph 的边界

1. 为什么订单号、流水号优先走规则，而不是全部交给模型分类？

明确标识符是高精度信号，规则可解释、可测试且不会因模型波动改变。先识别订单号或支付流水号，再由模型处理“我刚付了钱”这类模糊语句；识别结果仍需参数校验和用户归属核验。

追问：订单号格式升级了怎么办？答：把规则放在版本化配置与回归样本中，不在提示词里散落复制。

2. 一句话同时问商品价格和订单物流，图怎么走？

先拆成商品与物流两个意图；商品可公开查询，物流必须先鉴权并确定具体订单。若缺订单引用，先追问，不把向量命中的商品误当作用户已购买的商品。结果汇总时标明每条事实来自哪个 Tool。

追问：两个 Tool 一个成功一个超时？答：分别呈现已核实部分与未完成部分，不用成功结果补全失败结果。

3. 低置信度路由为何要追问，而不是挑分数最高的 Agent？

最高分只表示相对排序，不表示足够确定。像“那个怎么还没到”可能指商品、订单或物流；错误路由会触发不必要的业务查询。设置校准过的阈值和冲突规则，追问最少的关键槽位，例如订单号或商品型号。

追问：如何定阈值？答：在标注意图集上看误路由成本、澄清率与实际业务风险，不能凭感觉写 0.8。

4. LangGraph 比单个大 Prompt 多解决了什么？

它把检索、鉴权、业务查询、校验、生成和人工转接拆成可观察的节点与条件边。每个节点有输入输出约束；失败能定位到具体阶段，待补参数或人工确认也可从 checkpoint 恢复。

追问：图是否越细越好？答：按需要独立重试、授权或观测的边界拆节点，避免把每个字符串处理都做成节点。

检索与商品事实

Milvus 召回不等于交易事实

5. Milvus 向量检索和商品业务接口分别负责什么？

向量检索负责找可能相关的候选商品；业务接口负责当前上架状态、SKU 规格、价格、押金与库存。推荐前对候选做型号、容量等硬条件过滤，再查询业务事实；不能因为向量相似就推断商品可租。

追问：业务接口价格与向量库不一致？答：使用业务接口价格，并记录向量索引需要更新。

6. 为什么“iPhone 18 Pro”不能直接子串匹配“Pro Max”？

Pro 是 Pro Max 的前缀，子串判断会混淆两个 SKU 家族。应规范化空格与大小写、识别代际边界和明确版本；只说“iPhone 18”可按系列处理，明确说 Pro 时必须排除 Pro Max。

追问：`iPhone180` 呢？答：代际数字必须整体比较，不能让 `18` 命中 `180`。

7. `12GB+512GB` 这种规格怎样处理？

先识别这是运行内存加存储容量的组合，用户说“512GB”通常指后面的存储；不能把前面的 12GB 当存储匹配。最好在入库时结构化为 RAM 与 storage 字段，查询时按明确槽位过滤；历史数据可在读取层做兼容解析。

追问：用户只说“12GB 内存”怎么办？答：标注 RAM 槽位，不按 512GB 存储去匹配。

8. 商品变更后如何同步向量库？

以商品 ID 作为稳定主键，对名称、规格、说明等影响语义的字段重新生成向量并 upsert；价格、库存等高频动态字段优先由业务接口读取。下架时及时移出候选或在检索后强制拦截，不能只等索引定时重建。

追问：怎样避免每次全量重算？答：根据业务变更事件或内容版本只处理变化的商品，同时设置补偿性的全量对账。

9. SPU、SKU 和向量索引的粒度怎么选？

SPU 适合语义召回“哪款机型”，SKU 才承载容量、颜色、成色与实时价格。可按 SPU 或商品说明建向量，再用业务 SKU 列表过滤；若每个 SKU 文案差异很大，才考虑 SKU 级向量。无论哪种，最终展示必须落到可核验的业务 ID。

追问：同款不同容量有多个报价？答：给出明确 SKU 与对应报价，不能拿最低价替代全部容量。

Tool 与用户鉴权

模型提出查询，服务端决定能否执行

10. 如何设计订单查询 Tool 的参数？

使用受控 schema，例如订单号、查询范围和分页参数；拒绝任意 URL、SQL、用户 ID 等模型自由拼出的参数。登录用户 ID 由服务端鉴权上下文注入，不能由模型或请求体决定。

追问：模型传了别人的 userId？答：忽略或拒绝，绝不作为权限依据。

11. 登录鉴权和订单归属鉴权有什么不同？

登录鉴权证明请求者是谁；归属鉴权证明这张订单属于请求者。二者都要做，并在业务服务或 Tool 网关校验。浏览器 Cookie 仅用于会话续接时，不能代替真实登录身份。

追问：同浏览器切换账号？答：按新 userId 隔离会话和缓存，旧账号订单引用不能复用。

12. 支付流水与物流查询为何还要单独核验归属？

知道流水号或运单号不代表有权查看。应先把流水或物流记录关联到订单及登录用户，再返回可展示字段；跨用户查询不能泄露金额、收件地址、是否存在等敏感细节。

追问：物流服务只返回运单号怎么办？答：先在订单域校验归属，再按受控运单号查物流，并核对关联关系。

13. Tool 超时、查无记录和 5xx 能用同一段兜底话术吗？

不能。查无记录是确定性业务结果；超时是不知道结果，适合有限重试与稍后查询；5xx 需要记录故障并转人工或提示服务不可用。把超时说成“没有订单”会制造错误业务事实。

追问：重试几次？答：按幂等性、接口超时预算与退避策略设置上限，不能无限重试。

14. 用户要求退款，Agent 应调用退款 Tool 吗？

在这个目标业务流程中不自动退款。Agent 识别诉求、核验登录态和可引用的订单，提供人工服务转接所需的最少上下文；实际退款由人工按业务流程确认。不能把“已转接”说成“已退款”。

追问：人工工单创建失败？答：如实说明尚未转接成功，提供可用的人工渠道，不伪造工单号。

会话与持久化

能恢复流程，也要防止旧事实复活

15. MySQL checkpointer 存什么，不存什么？

保存 LangGraph 的 thread_id、节点状态、待补参数、当前商品或订单引用以及最近对话，使进程重启后能续接。不要把价格、库存、支付状态当成永久真值；下一轮需要重新查业务接口。敏感数据按最小化与保留期管理。

追问：为什么不只存聊天文本？答：文本无法可靠表达流程停在哪个节点、哪个参数待补或 Tool 是否已执行。

16. thread_id 如何设计，避免跨用户串会话？

服务端由可信登录 userId 与会话 ID 生成或映射 thread_id，查询 checkpoint 时同时校验用户身份。不能直接采用前端传来的 userId，也不能仅凭匿名 Cookie 访问真实订单状态。

追问：用户退出登录？答：失效会话绑定；再次登录按身份恢复或创建会话，不能借旧 Cookie 读取他人状态。

17. 长对话为什么要保留“焦点”而不只做摘要？

摘要容易漏掉精确 SKU、订单引用或待补容量。保留最近几轮原文与结构化焦点，早期内容再压缩为摘要；动态金额和状态不写入可长期复用的摘要。

追问：用户说“那 256G 呢”？答：沿用当前机型焦点，仅更新容量槽位，并重新查询商品事实。

18. checkpoint 恢复后如何防止重复执行 Tool？

只读查询可在预算内重试；有副作用的 Tool 必须用业务幂等键与状态机防重。图的 checkpoint 能恢复流程，但不能替代业务系统的幂等约束和事务边界。人工转接也要防止重复建工单。

追问：节点已执行但 checkpoint 写入失败？答：以业务幂等记录作为最终依据，恢复时先核对执行结果。

可靠性与线上排障

让回答可核验，让失败可定位

19. 怎样约束模型不编造订单号、金额和状态？

将 Tool 结果作为结构化证据，生成后校验回答中的 ID、金额、状态是否存在于已授权的返回数据。不存在或冲突时不给模型自由补全，应返回无法核实或转人工；提示词只是辅助，不是最终防线。

追问：候选商品中的描述含恶意指令？答：作为不可信数据处理，不能让它改变系统指令或工具权限。

20. 为什么向量命中了商品，页面却说没有？怎么定位？

沿链路分别记录原始向量 Top-K、型号与容量过滤后的候选、业务接口核验结果和模型选中的 ID。项目实测发现 OPPO、vivo、iPad 的相关商品已进入 Top-10，却被型号连写和“12GB+512GB”解析误删；修正过滤后，20 条标注查询的最终候选集合由 16/20 提升到 20/20。

追问：这能说明向量召回也提升了吗？答：不能，原始 Recall@10 仍约 0.839，修复发生在召回之后。

21. 商品价格变了，但向量库还是旧价，如何避免错误承诺？

把向量库价格视为参考字段；展示前调用商品业务接口取当前报价、押金与库存，无法核实时不报确定价格。同步任务可更新索引，但不能把“同步及时”作为唯一正确性保障。

追问：业务接口超时？答：可展示机型信息，但明确价格未核实，不使用旧索引价冒充实时价。

22. 服务上线后健康检查 200，聊天仍 503，怎么查？

健康检查只证明进程能响应。分别检查 Embedding 密钥和维度、Milvus URI/集合、向量模型一致性、LLM 返回格式、业务 Tool 连通性与超时；按请求 ID 串联节点日志，避免仅凭 200 健康状态判断全链路可用。

追问：如何减少排障暴露隐私？答：日志保留耗时、状态码、脱敏的标识符和节点名，不写密钥与完整订单信息。

评测与复盘

指标先定义对象，再谈数字

23. Recall@10 与 MRR 的区别是什么？

Recall@10 看所有相关商品有多少进入前 10；MRR 只看第一个相关商品的名次。前 10 找到 3/4 个相关商品，Recall@10 是 0.75；如果第一个排在第 2，倒数排名是 0.5。两者反映覆盖与首个命中的排序，不能互相替代。

追问：没有相关商品的负例怎么算？答：通常不进入这两项分母，另测“无结果时不乱推荐”的正确率。

24. 为什么离线过滤 12/12 不等于真实 Milvus 召回 100%？

离线用固定候选池，跳过 Embedding 和 Milvus，只测过滤函数。真实评测要对当前集合人工标注相关 ID，实际生成向量并查询 Top-K。此项目的 20 题真实评测里，最终候选 20/20 与标注集合一致，但原始向量 Recall@10 约 0.839。

追问：最终候选为何比原始 Top-10 好？答：项目对明确型号额外查询集合补全候选，两个阶段须分开报告。

25. 评测集如何避免只测“容易的成功样本”？

按意图、型号版本、容量、价格边界、查无结果、跨用户鉴权、多意图、Tool 超时与转人工分层抽样。每题固定期望商品 ID 或业务动作，标注版本和数据快照；失败样本保留为回归用例，不因修复而删掉。

追问：商品数据更新后标签怎么办？答：重新核对上架、规格、价格和 ID，再重跑，不能沿用过期真值。

26. 面试官问“你这个项目哪些已上线、哪些只是设计”，怎么回答？

按证据分层说明：当前 Python 仓库可运行 Milvus 商品检索、LangGraph 流程和 SQLite checkpoint，订单/退款是模拟流程；MySQL、真实 Java Tool、登录与归属鉴权、退款转人工若在其他服务已落地，就展示其接口与测试证据，否则明确说是目标设计。不要把模拟订单测试写成真实交易能力。

追问：最有说服力的演示？答：真实集合的标注查询、逐题失败复盘、跨用户拒绝用例和工具调用审计。

LangChain / LangGraph 专题

从组件组合到有状态工作流

27. LangChain 的 Runnable 链与 LangGraph 的图，分别适合什么场景？

Runnable 适合输入到输出较明确的组合，例如提示词、模型、结构化解析、检索器的顺序或并行处理；可统一调用、批处理和流式输出。LangGraph 适合有条件分支、循环、待补参数、人工介入和跨轮恢复的流程。可以把一个 Runnable 作为图中的节点，不必二选一。

追问：只做一次商品摘要需要图吗？答：通常先用简单 Runnable；当路由、状态与恢复成为真实需求再上图。

28. LCEL 中如何组合检索、并行输入与结构化输出？

用 Runnable 组合把用户问题和检索证据送入提示词、模型及解析器；独立输入可以并行生成，但有依赖的步骤仍需顺序执行。模型输出必须经过 schema 校验，商品 ID 只能从候选列表中选择，解析成功也不等于业务事实正确。

追问：并行检索商品与订单安全吗？答：订单查询先完成登录和归属鉴权；不能为了并行绕过权限节点。

29. bind_tools 与真正执行 Tool 是同一回事吗？

不是。绑定工具 schema 让模型能够提出带参数的调用；服务端执行前仍要校验工具白名单、参数、登录身份和数据归属。执行结果以对应的工具调用 ID 回填，再让模型生成回答。模型提出“退款”不代表系统获准执行退款。

追问：ToolNode 能代替鉴权吗？答：不能，鉴权必须在工具实现或受控网关里执行。

30. LangGraph State 中的 reducer 解决什么问题？

节点返回的是状态更新；普通字段默认由新值覆盖，消息列表这类需要累积的字段可配置 reducer（如 add_messages）。并行节点若同时更新同一个没有合适 reducer 的字段，会产生冲突或丢数据。State 应保存必要引用和流程状态，避免把巨大检索结果无限累积。

追问：价格和库存适合累积在 State 吗？答：不适合长期当真值，后续轮次需重新查业务接口。

31. 条件边与 Command 路由有什么区别？

条件边根据当前 State 选择下一个节点，适合显式的路由函数；Command 可以在节点结果中同时表达状态更新与下一步去向。无论选择哪一种，都要为无法识别的意图、工具失败和澄清请求设置合法出口，避免图走到不存在的节点。

追问：多意图如何路由？答：先决定拆分还是追问，再进入受权限约束的分支，不能只取模型第一个标签。

32. interrupt / resume 和 checkpointer 要一起怎么用？

图编译时绑定 checkpointer，调用时提供稳定的 thread_id；节点调用 interrupt 暂停并保存状态，用户回应后用相同线程和 resume 值继续。恢复可能重新执行中断节点中 interrupt 之前的代码，因此副作用应放在确认之后，并用业务幂等键保护。

追问：只传相同用户 ID 足够吗？答：还需会话隔离和服务端登录校验，避免不同会话串状态。

33. 什么时候用子图或多 Agent，什么时候只用一个图？

商品、订单、流水流程若各有独立状态、工具和测试边界，可以拆子图；主图负责鉴权、路由、汇总与失败兜底。多 Agent 会增加消息转交、权限和观测成本，不能只因任务名称不同就拆多个会自行行动的模型。

追问：子图返回订单结果给主图时？答：只传已授权、已校验的结构化结果与必要引用，不泄露完整内部状态。

34. 怎样测试和观测一个 LangGraph 工作流？

分别测节点纯逻辑、条件边、工具异常、checkpoint 恢复与端到端请求；使用测试替身覆盖超时、空结果和跨用户拒绝。线上记录每个节点的耗时、路由决策、工具状态和脱敏 trace ID，流式输出时区分模型片段、工具事件和最终事实。

追问：图测试全通过就能说业务链路正常吗？答：不能，还需用真实依赖做小规模冒烟和标注集评测，并报告未覆盖的接口。

练习方法

先用 45 秒说出结论、设计依据和失败边界；再展开每题核对。面试回答尽量引用真实记录：20 条商品查询、Recall@10 约 0.839、MRR 0.750，以及 4 个过滤失败如何定位并修复。没有实现的业务接口要明确说明。
